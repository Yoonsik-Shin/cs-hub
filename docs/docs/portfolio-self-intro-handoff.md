# Self-Intro 포트폴리오 전달 초안

이 문서는 `self-intro` 저장소에 바로 반영하지 않고, CS Hub의 현재 코드와 Git 이력에서 확인한 사실을 포트폴리오 문구로 옮기기 위해 정리한 전달 자료다.

- 기준 브랜치: `refactor/portfolio-readiness`
- 기준 커밋: `292bbb0`
- 작성 원칙: 코드, 테스트, 설정 또는 커밋으로 확인할 수 없는 성과는 확정 문구로 쓰지 않는다.
- 적용 상태: **초안만 작성했으며 `self-intro`에는 미반영**

## 한 문장 정의

이메일·네이버 카페·구글 시트·전화로 흩어진 고객 문의를 한 화면에서 처리하고, 중복 수집·이메일 회신 연결·완료 문의 재오픈·개인정보 보호·외부 자동화 실패 같은 운영 경계를 코드로 다룬 멀티채널 CS 운영 시스템입니다.

## Self-Intro 경험 항목 초안

### 제목

`[청년 일경험] 멀티채널 CS 운영 시스템 설계·구축`

기존의 “고객문의 수집 및 CS 통합 관리 페이지 구현”보다 단순 화면 구현이 아니라 수집 파이프라인과 운영 정책까지 맡았다는 점을 드러낸다.

### 요약

이메일·네이버 카페·구글 시트·전화로 분산된 고객 문의를 통합 수집하고 처리 이력을 관리하는 웹 기반 CS 운영 시스템을 구축했습니다. Spring Boot API, React 운영 화면, n8n 수집 워크플로, Playwright 브라우저 워커를 연결했으며, 채널별 중복 방지와 이메일 스레드 연결, 완료 문의 자동 재오픈, PII 암호화, 서비스 간 인증 경계를 구현했습니다.

### 핵심 회고

기능을 연결하는 데 그치지 않고 재시도에 따른 중복, 회신 맥락 유실, 암호화된 데이터의 검색, 세션 만료와 외부 자동화 실패처럼 운영 중 발생할 경계를 먼저 식별하고 정책·테스트·문서로 고정하는 경험을 했습니다.

## 상세 사례 초안

Self-Intro의 `experience_detail` 구조에 맞춰 `상황 → 과제 → 행동 → 결과`로 정리했다. 공개 화면에는 아래 사례 중 3~4개만 노출하고, 나머지는 면접 답변 또는 상세 문서 링크로 사용하는 편이 좋다.

### 1. 멀티채널 문의 수집과 중복 방지

**상황**

이메일, 네이버 카페, 구글 시트 등 채널마다 식별자와 메타데이터 형식이 달랐고, 폴링과 워크플로 재시도로 동일 문의가 여러 번 저장될 수 있었습니다.

**과제**

채널별 입력 차이는 보존하면서 하나의 문의 모델로 통합하고, 같은 요청이 반복되어도 중복 문의가 만들어지지 않는 저장 경계를 설계했습니다.

**행동**

- 채널별 메타데이터를 다형 타입으로 역직렬화하고 입력 계약을 검증했습니다.
- 채널 고유 식별자에서 문의 고유키를 생성해 저장 경계에서 중복을 차단했습니다.
- 통합 유스케이스는 흐름 조율만 담당하게 하고, 이메일 입력 검증·관리자 발송 필터·웹메일 URL·발신자 해시 정책을 별도 컴포넌트로 분리했습니다.
- n8n 수집 워크플로에는 채널별 실행 lock과 동일 오류 반복 알림 억제를 적용했습니다.

**결과**

서로 다른 채널 입력을 동일한 문의 처리 흐름으로 모으면서도, 재수집과 재시도에 의해 같은 문의가 중복 적재되는 위험을 코드와 저장 제약으로 제어했습니다.

**코드 근거**

- `IntegrateInquiryDataUseCase`
- `InquiryUniqueKeyGenerator`
- `EmailIntegrationValidator`
- `AdminEmailSenderPolicy`
- `infra/n8n/scratch_workflow.json`
- 주요 커밋: `66f476b`, `6096c69`, `354d504`, `92ad4b7`

### 2. 이메일 회신 스레드 연결과 완료 문의 재오픈

**상황**

고객의 이메일 회신이 매번 새 문의로 저장되면 상담 맥락이 분리되고, 이미 완료 처리한 문의의 후속 질문을 놓칠 수 있었습니다.

**과제**

명시적인 이메일 헤더를 우선 사용하되 헤더가 부족한 경우에도 보수적으로 부모 문의를 찾고, 완료 문의에 후속 회신이 들어오면 상태와 감사 이력을 함께 갱신해야 했습니다.

**행동**

- `In-Reply-To`, `References` 순으로 부모 메시지를 찾고, 마지막 수단으로 최근 7일의 발신자 HMAC과 정규화 제목을 비교했습니다.
- 회신의 회신도 최초 부모 ID에 연결해 스레드가 여러 단계로 쪼개지지 않게 했습니다.
- 부모가 `RESOLVED` 상태일 때만 `OPEN`으로 되돌리고 시스템 작업 이력을 남겼습니다.
- 시간과 시스템 작업자 정보를 주입 가능한 경계로 분리해 회귀 시나리오를 테스트했습니다.

**결과**

후속 이메일을 기존 문의 맥락에 연결하고, 완료 문의의 추가 질문을 자동으로 다시 열어 상태 누락을 방지하는 처리 흐름을 만들었습니다.

**코드 근거**

- `EmailThreadResolver`와 `EmailThreadResolverTest`
- `ResolvedInquiryReopener`와 `ResolvedInquiryReopenerTest`
- `SystemOperatorProvider`
- ADR `001-email-thread-resolution.md`
- 주요 커밋: `d6179fa`, `8cc0d52`, `18c4f92`, `3e8b2dc`

### 3. 개인정보 암호화와 검색 경계 분리

**상황**

문의 본문, 이메일, 전화번호와 외부 서비스 세션은 저장 시 보호해야 했지만, 무작위 IV를 사용하는 암호문만으로는 이메일 발신자 기준 등치 검색을 할 수 없었습니다. 기존 평문 데이터와 신규 암호문이 한동안 함께 존재할 가능성도 고려해야 했습니다.

**과제**

민감정보를 인증된 암호화 방식으로 저장하면서 검색 가능성과 기존 데이터 호환성을 별도 경계로 설계했습니다.

**행동**

- JPA `AttributeConverter`와 JSON 필드용 Jackson Mixin에 AES-GCM 저장 암호화를 적용했습니다.
- 매 암호화마다 무작위 IV를 사용하고 GCM 인증 태그가 다른 위변조 암호문을 거부하도록 테스트했습니다.
- 이메일 검색에는 원문이나 결정적 암호문 대신 HMAC-SHA256 보조값을 사용했습니다.
- 신규 값은 암호화해 저장하고 레거시 평문은 읽을 수 있는 전환 경로와, 실행 애플리케이션에서 분리한 독립 마이그레이션 도구를 마련했습니다.

**결과**

저장 기밀성, 위변조 탐지, 발신자 검색, 점진적 데이터 전환을 한 암호화 함수에 뒤섞지 않고 각각의 책임으로 분리했습니다.

**코드 근거**

- `PiiEncryptionUtils`, `AesGcmCipher`
- `EncryptedStringConverter`
- `PiiAwareObjectMapperConfig`, `PiiJacksonMixins`
- `PiiEncryptionMigrationTool`
- `PiiEncryptionUtilsTest`, `EncryptedStringConverterTest`
- ADR `002-pii-storage-and-search.md`
- 주요 커밋: `4f2ba91`, `27abacd`

### 4. 관리자·API·브라우저 워커 사이의 신뢰 경계

**상황**

관리자 브라우저 요청과 n8n·Playwright 같은 내부 자동화 요청은 호출 주체와 노출 범위가 달라 하나의 인증 방식으로 처리하기 어려웠습니다. 외부 사이트 세션과 일회용 로그인 값이 로그나 응답에 노출되지 않도록 해야 했습니다.

**과제**

사용자 접근, 애플리케이션 권한, 서비스 간 호출을 서로 다른 경계로 나누고 내부 토큰의 누락과 잘못된 기본값을 시작 단계에서 차단했습니다.

**행동**

- Nginx Basic Auth가 인증한 사용자명을 덮어쓴 `X-Remote-User` 헤더로 API에 전달하고, DB 역할과 Spring Security 인가를 연결했습니다.
- API와 브라우저 워커 사이에는 별도의 `X-Internal-Token`을 사용했습니다.
- 워커는 토큰 누락·짧은 값·알려진 placeholder 설정 시 기동을 거부하고 요청 토큰을 상수 시간으로 비교합니다.
- 네이버 일회용 로그인 코드가 로그에 남지 않도록 제거하고, 세션 쿠키는 용도별 키로 암호화해 저장했습니다.

**결과**

운영자 인증과 내부 서비스 인증을 분리하고, 잘못된 보안 설정이 조용히 허용되지 않도록 fail-fast 검증과 회귀 테스트를 갖췄습니다.

**코드 근거**

- `RemoteUserAuthenticationFilter`, `SecurityConfig`
- `apps/browser-worker/src/security/internalToken.js`
- `EncryptionUtils`
- ADR `003-worker-internal-token.md`
- 주요 커밋: `dea0ea5`, `3c5f867`

### 5. 자동 갱신 중 운영자 화면 맥락 보존

**상황**

문의 목록을 주기적으로 갱신하는 동안 선택한 상세 문의가 바뀌거나, 페이지를 넘겼을 때 이전 일괄 선택이 사라지는 문제는 운영자의 작업 실수로 이어질 수 있었습니다. 상세 패널 한 곳에 목록·선택·타임라인·이미지 상태가 모여 있어 변경 위험도 컸습니다.

**과제**

서버 데이터가 갱신되어도 사용자가 보고 있던 문의와 일괄 작업 맥락을 보존하고, 상태 정책을 DOM 없이 검증할 수 있게 구조를 나눴습니다.

**행동**

- 페이지 캐시, 목록 병합, 일괄 선택, 선택 문의 보존 규칙을 순수 TypeScript 정책으로 분리했습니다.
- 타이머 생명주기는 `useAutoRefresh` 훅으로 이동했습니다.
- 작업 로그·회신 타임라인과 첨부 이미지 탐색·확대 상태를 전용 컴포넌트로 추출했습니다.
- 합성 fixture 기반 showcase 서버로 데스크톱·이미지 뷰어·390px 화면을 재현하고 실제 고객정보 없이 화면 증거를 만들었습니다.

**결과**

자동 갱신과 페이지 이동 중에도 같은 문의의 상세와 유효한 선택을 유지하는 규칙을 독립적으로 테스트할 수 있게 했고, 대형 상세 컴포넌트의 변경 범위를 줄였습니다.

**코드 근거**

- `pageCache.ts`, `inquiryListLoader.ts`, `batchSelection.ts`, `selectedInquiry.ts`
- `useAutoRefresh.ts`
- `AdminSidebar.tsx`, `OperatorWidget.tsx`, `NaverSessionWidget.tsx`
- `useInquiryActivity.ts`, `useInquiryFieldEditor.ts`
- `InquiryMetadataSections.tsx`, `InquiryActionModal.tsx`

- 주요 커밋: `ceedb5a`, `67cb908`, `39a4e12`, `7d6d712`, `5cb951d`

## 기술 스택 표기 권장안

기술 이름을 한 덩어리로 압축하기보다 코드에서 역할을 설명할 수 있는 단위로 나눈다.

- Backend: Java 21, Spring Boot 3, Spring Data JPA, Querydsl, Flyway
- Frontend: React 19, TypeScript, Vite
- Automation: n8n, Node.js, Express, Playwright
- Data/Storage: PostgreSQL 16, MinIO, AES-GCM, HMAC-SHA256
- Infra/Observability: Docker Compose, Nginx, Grafana, Loki, Grafana Alloy
- Documentation/Test: Docusaurus, JUnit 5, Node test runner, ESLint

## 공개 화면 배치 권장 순서

1. 한 문장 문제 정의
2. 이메일 스레드 연결과 재오픈
3. PII 암호화와 검색 분리
4. 내부 서비스 신뢰 경계
5. 자동 갱신 중 사용자 맥락 보존

첫 화면에는 기능 목록보다 “운영에서 깨지는 경계를 어떻게 다뤘는가”를 먼저 보여준다. 채널 수집 자체는 배경으로 두고, 이메일 회신·암호화 검색·자동 갱신 상태처럼 코드 판단이 드러나는 사례를 전면에 둔다.

## 추가 확인이 필요한 사용자 증거

다음 내용은 소스 코드만으로 확정하지 않고, Self-Intro 반영 시 본인의 기록으로 한 번 더 확인한다.

- 실제 회사 환경에 배포했는지, 별도 검증 환경 또는 로컬 시연까지였는지
- 본인이 단독으로 맡은 범위와 다른 참여자가 담당한 범위
- 실제 운영 사용 기간과 사용자 수
- 기존 문의 처리 시간, 누락률, 중복률의 전후 수치
- 독립 PII 마이그레이션 도구로 운영 데이터 이관을 완료했는지
- 카카오 채널이 실제 운영 수집 범위였는지 또는 테스트용 지원 타입인지

위 항목이 확인되기 전에는 효과나 기여도를 숫자로 만들지 않는다.

## 적용 시 작업 단위

`self-intro`의 현재 대규모 작업이 끝난 뒤 다음 순서로 별도 브랜치에서 반영한다.

1. 현재 운영 DB 콘텐츠와 최신 Flyway 마이그레이션을 다시 확인한다.
2. 경험 ID에 의존하는 기존 상세 항목과 공개 여부를 확인한다.
3. 경험 요약·회고와 상세 사례를 한 개의 새 Flyway 마이그레이션으로 갱신한다.
4. 기술 스택 연결은 기존 스킬 ID를 조회해 중복 없이 갱신한다.
5. 로컬 DB에 마이그레이션을 적용하고 공개 경험 API 응답을 확인한다.
6. 프로젝트 상세 화면과 인쇄 화면을 함께 캡처해 문장 길이와 줄바꿈을 검증한다.
