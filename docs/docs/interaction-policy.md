# 상호작용 및 업무 정책

같은 기능이 화면이나 진입점에 따라 다르게 동작하지 않도록 표현, 입력, 오류, 트랜잭션 경계를 한곳에서 소유한다.

## 프론트엔드 단일 정책 경계

| 대상 | 소유 코드 | 적용 원칙 |
| --- | --- | --- |
| 상태·채널·날짜 | `features/inquiry/policy.ts` | 라벨과 포맷을 컴포넌트에서 다시 정의하지 않는다. |
| 상태 변경 사유 | 프론트엔드 `policy.ts`, 백엔드 `InquiryPolicy` | 최소 길이와 안내 문구를 모든 단건·일괄 진입점에 동일하게 적용한다. |
| 사용자 코드 | 프론트엔드 `policy.ts`, 백엔드 `InquiryPolicy` | 숫자 정규화와 12자리 계약을 생성·수정·웹훅에서 공유한다. |
| 이미지 | `policy.ts`, `imageProcessing.ts` | 생성과 상세 편집에 같은 개수·MIME·크기·압축 규칙을 적용한다. MIME별 presigned URL 요청을 분리한다. |
| HTTP | `api/httpClient.ts` | 직접 `fetch`하지 않고 JSON·텍스트 오류를 같은 `HttpError`로 변환한다. |
| 모달 | `components/ui/ModalSurface.tsx` | portal, focus trap, Escape, 초기·복귀 포커스, body scroll lock을 공유한다. |
| 사용자 피드백 | `FeedbackProvider`, `InlineAlert` | 전역 결과는 toast, 현재 입력의 오류는 inline, 중단 가능한 작업은 비동기 확인창을 사용한다. |

비동기 폼은 상위 콜백이 완료될 때까지 기다린다. 성공 전에 모달을 닫거나 입력을 초기화하지 않으며, 실패하면 입력 맥락과 오류를 유지한다. 서로 다른 조회가 겹칠 수 있는 목록 요청은 요청 순번을 비교해 오래된 응답이 최신 상태를 덮어쓰지 않게 한다.

## 백엔드 업무 단위

- 한 상세 저장에 포함된 상태 변경과 필드 수정은 `UpdateInquiryUseCase`에서 한 트랜잭션으로 처리한다.
- 답변 또는 메모 등록과 선택적 상태 변경은 `RegisterInquiryWorkLogUseCase`에서 한 트랜잭션으로 처리한다.
- 수정 사유는 어떤 변경도 시작하기 전에 모두 검증한다.
- 이미지 객체 삭제는 DB 트랜잭션이 커밋된 뒤 실행해 롤백된 문의가 파일을 잃지 않게 한다.
- 일괄 상태 변경은 UI에서 선택한 ID 집합을 그대로 보내며, 선택 개수에 따라 암묵적으로 필터 전체 처리로 바꾸지 않는다.
- 관리자 계정은 DB를 먼저 flush한 뒤 `.htpasswd`를 갱신한다. 파일은 같은 디렉터리의 임시 파일로 쓴 뒤 원자적으로 교체하고, DB 롤백 시 이전 인증 항목을 복원한다.

## 오류와 부분 성공

작업 실행 오류와 보조 조회 오류를 같은 상태에 넣지 않는다. 예를 들어 상세 타임라인의 회신 조회가 실패해도 이미 가져온 작업 이력은 표시하고, 해당 영역에만 오류를 노출한다. 반대로 사용자가 제출한 명령의 실패는 입력 영역 가까이에 표시한다.

외부 저장소는 DB 트랜잭션에 직접 참여하지 못한다. 따라서 가능한 작업은 커밋 이후로 미루고, 함께 바뀌어야 하는 인증 파일은 이전 값을 보관해 롤백 보상한다. 보상 자체가 실패하면 로그로 남겨 운영자가 복구할 수 있게 한다.

## 회귀 방지

`apps/frontend/tests/conventionGuard.test.ts`는 다음 우회를 빌드 전에 탐지한다.

- `api/httpClient.ts` 밖의 직접 `fetch`
- `alert`, `prompt`, 브라우저 기본 `confirm`
- `ModalSurface` 밖에서 표준 `modal-overlay`를 직접 구성하는 구현

도메인 정책은 `policy.test.ts`, 계정 입력 계약은 `accountPolicy.test.ts`, HTTP 오류 계약은 `httpClient.test.ts`가 예제로 고정한다. 백엔드 복합 명령과 저장소 보상은 각 유스케이스 단위 테스트로 검증한다.
